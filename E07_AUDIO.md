# E07: штатный микрофон для русского ASR

Полный исходный порт вынесен в отдельную ветку
[`dionisboss:e07/native-se`](https://github.com/dionisboss/changan-a06-ru-assistant/tree/e07/native-se/e07):
точные Java-исходники рабочей сборки, smali-патчер, сборщик, проверки и
[сравнение STT/TTS с A06](https://github.com/dionisboss/changan-a06-ru-assistant/blob/e07/native-se/e07/AUDIO_COMPARISON.md).

На E07 подтверждён путь **штатный захват → SE → GigaAM → русский маппер → штатный
обработчик → русский TTS** без отдельного `AudioRecord` в русском распознавателе.
Ниже — контракт и результат отдельного порта, проверенного 14.09.2026. Этот документ
не добавляет поддержку E07 в сборщик и не является инструкцией установки APK A06 на E07.

## Применимость к A06

В v1.0.5 и `main` на `a6081a5` уже используется штатный звук:
[build_sa.sh](stand/build_sa.sh) подключает `RuBridge.feed` к
`SrBaseSession.lambda$registerAsrDataCallBack$5$com-incall-apps-speechassistant-sr-SrBaseSession(IIJ[BI)V`.
[RuBridge](stand/asr-android/src/com/stand/bridge/RuBridge.java) передаёт PCM в
[GigaAsr](stand/asr-android/src/com/stand/asr/GigaAsr.java), используя `wp=1/3` для
начала/конца фразы. В этом пути нет собственного `AudioRecord`.

На исследованном E07 (Android 11, SpeechAssistant V17.0126 / code 20260318) этой
точки подключения нет. Звук доступен раньше — в `SeSession$2.appendData([BII)V`
перед `SrEngineProxy.appendAudioData([BI)V`. **Здесь байты ещё не являются PCM.**
Причин применять описанный ниже extractor к готовому PCM A06 не обнаружено.
Штатный A06-путь и его маркеры фразы остаются без изменений.

## Ошибка, которую нужно избежать при переносе

E07-callback сообщает `length=3584` и третий аргумент `2`, но Java-массив и заголовок
живого native-кадра задают **7168 байт**. Это контейнер `IFLYAUTOISS` с несколькими
секциями. Копирование только `length` может обрезать нужную секцию; передача всего
контейнера в GigaAM тоже неверна. Третий аргумент не задаёт канальность готового PCM.

При ошибочной подаче 3584 байт как PCM получалось примерно 226 КБ/с вместо 32 КБ/с.
Лимит «15 секунд» заполнялся за несколько реальных секунд, ASR возвращал мусор.
Буквы `LY` и `AU` из заголовка при чтении как PCM16LE дают отсчёты 22860 и 21825:
большие пики в такой записи сами по себе не доказывают наличие речи.

Контракт установлен по OEM-классам `ISSSeImpl`, `PcmConvertor`, `SeSession` и
`PcmRecorder` из штатного APK E07, затем проверен на живом потоке. Смещения ниже
относятся к этой версии, а не ко всем прошивкам iFlytek.

| Поле | Смещение / значение |
|---|---|
| Сигнатура | Байты 0–15: ASCII `IFLYAUTOISS` и пять нулей |
| Заголовок | 512 байт |
| Полная длина контейнера | LE32 без знака по смещению 20 |
| Число секций | LE32 без знака по смещению 24 |
| Дескрипторы | С 64, по 16 байт: `type`, `offset`, `buf`, `channels` (LE32) |
| Данные секции | Начало `512 + offset`, длина `buf * channels` |
| Речевой выход | 256 отсчётов = 512 байт, mono PCM16LE / 16 кГц на кадр |

Штатный `SeSession.getInstance().processPcmData(4, frameCopy, 2)` выбирает ASR
**type 2 в MAB** или OMNI **type 4 в MAE**. Первый аргумент `4` — запрос extractor,
а не безусловный выбор секции type 4. Запрос `3` в MAB объединяет ASR и VAD и
не подходит как mono-речь для GigaAM. Штатный extractor также преобразует
многоканальные planar-данные в interleaved; проверенный русский вход принимает
только речевую секцию `buf=512`, `channels=1`.

## Как устроен работающий вход E07

1. Хук стоит у конкретного вызова `SrEngineProxy.appendAudioData` внутри
   `SeSession$2.appendData`, после штатных проверок. `PcmRecorder`, SE, wake listener,
   проверки разрешений, направление и последующие exporters сохранены.
2. До возврата callback копируется полный кадр по проверенной длине из заголовка.
   Проверки: `0 < callbackLength <= array.length`, `512 <= headerLength <= 65536`
   и `headerLength <= array.length`. Усечённый массив не дополняется нулями.
3. В рабочем потоке перед OEM-extractor проверяются сигнатура, число секций
   `1..28`, уникальность типов и границы **всех** дескрипторов. Для беззнаковых
   полей проверка произведения делается через деление, чтобы избежать overflow:
   при `buf != 0` требуется `channels <= (headerLength - 512 - offset) / buf`;
   сначала проверяется сам `offset`. Пустые секции разрешены.
4. Непустые речевые дескрипторы type 2/4 должны иметь `buf=512`, `channels=1`.
   Результат OEM-extractor проверяется по длине и побайтно сопоставляется с такой
   секцией. Нельзя выбирать «самый громкий канал»: это может оказаться музыка.
5. Callback только копирует кадр в очередь на 32 элемента (около 512 мс), сохраняя
   время поступления и состояние TTS. Извлечение и распознавание выполняются вне
   callback. Повреждение, переполнение, разрыв потока более 500 мс или явная
   остановка с необработанными кадрами запрещают decode частичной записи.
6. На время владения русской сессией пропускаются запуск и подача звука OEM SR;
   остальные ветки штатного фронтенда продолжаются. Поэтому фазы OEM SR здесь
   нельзя использовать для окончания русской фразы: нужен локальный endpoint
   по извлечённому PCM. В проверенной сборке сохранены порог RMS 1200, предел
   захвата 15 с и исключение TTS с хвостом 350 мс. Порог доступен для калибровки.
7. Отмена или новая сессия запрещает исполнение результата старого decode, даже
   если inference уже начался. Ошибка целостности остаётся запретом до конца сессии;
   последующий запрос остановки с decode не должен её сбрасывать.

Это требует адаптации жизненного цикла сессии E07, а не одной замены `feed()`.
Дополнительный MIC, изменение AudioPolicy или усиление для этого входа не нужны.
Установленный ранее обход MIC для сторонних приложений в AcsCenter оставался
включённым; русский ASR больше не читает его AudioRecord-поток. Работа всей системы
с полностью отключённым обходом этим испытанием не доказана.

## Подтверждённый результат и границы проверки

14.09.2026 в 10:11 МСК на E07 распознано «сколько осталось заряда батареи», маппер
передал `还有多少电` штатному обработчику. Полный ответ: «Заряд батареи: 55 процентов.
Запас хода: 247 километров». Владелец подтвердил хорошую слышимость и работу.

Ниже сокращённые строки журнала: оставлены время, аудиометрики и результат;
PID/TID и идентификаторы сессий опущены.

```text
10:11:15.755 RuBridge: RU session accepted direction=1 vadRms=1200 source=stock-se
10:11:19.881 RuBridge: RU capture end reason=silence-endpoint elapsed=4126 cancelled=false decode=true speech=true readBytes=132096 keptBytes=77312 dropBytes=53760
10:11:20.164 GigaAsr: decoded 38656 samples (2416ms) in 282ms: сколько осталось заряда батареи
10:11:27.359 TeraTts: playback end status=0 reason=drained frames=125424/125424 elapsed=7002
```

4126 мс — захват вместе с приветствием; 2416 мс — PCM после исключения TTS,
поданный в ASR; 282 мс — само распознавание на ГУ. Это разные интервалы.
SHA-256 проверенного **отдельного APK E07**:
`afd7b3a5c8c506ffb76f28e8e51fbb1774aba7ec2c72c7b0829fb3e1a993ca67`.
Он не является APK релиза A06 v1.0.5 и не публикуется этим PR.

Локальная проверка extractor с реальным OEM `PcmConvertor` прошла для MAB/MAE,
секций за пределами устаревшего callbackLength, повторного использования буферов,
повреждённых границ, unsigned overflow, дублей типов и неподдерживаемой канальности.
Для порта также проверялись захват/отмена, TTS, свежий DEX после обратного разбора
baksmali, подпись и соответствие APK исходникам. Эти проверки принадлежат отдельному
порту; они не означают, что сборщик этого репозитория уже умеет собирать E07.

Один успешный голосовой прогон не покрывает все места салона и фоновые условия.
Пассивный зонд, включённый позднее, не содержит эту команду. Предыдущие неудачные
SE-записи не становятся успешными задним числом; причина тихой ASR-секции в них
не установлена. **Слышимость в телефонных звонках остаётся отдельной задачей.**
